## 第 2 段：创建应用 + 密钥

```python
app = Flask(__name__)
app.secret_key = 'dev-only-change-this-in-production'
```

### 🔑 `Flask(__name__)` 是什么意思？

**★ 比喻：给餐厅挂牌匾。**

```
Flask 需要知道"我的店开在哪里"
__name__ 就是"当前位置"的标记
Flask 拿它去推算：
   "哦，店在 D:\study\flask-login\
    那后厨就是 D:\study\flask-login\templates\
    装饰品仓库就是 D:\study\flask-login\static\"
```

### 🔑 `secret_key` —— 这是重中之重

**★★★ 比喻：餐厅的【防伪印章】。**

```
★ 存包牌上要写"客户名叫张三，是贵宾"
★ 如果只是手写，顾客可以把"普通"改成"贵宾" —— 就冒充成功了
★ 所以餐厅要盖一个【只有自己知道的防伪章】
★ 顾客下次来，餐厅验章：
     章是真的 → 认牌
     章被改过 → 不认

★ secret_key 就是这个印章的图案
```

**★ 为什么不能泄露？**
```
印章图案泄露了 → 任何人都能伪造存包牌 → 全店沦陷
→ 所以真实项目里这个值必须随机、且不能提交到 Git
```

**★ 正确写法：**
```python
import os
app.secret_key = os.urandom(32)      # 每次启动随机生成
```

## 第 3 段：数据库连接函数

```python
DB_PATH = 'users.db'

def get_db():
    conn = sqlite3.connect(DB_PATH)
    conn.row_factory = sqlite3.Row
    return conn
```

**★ 比喻：每次要查仓库，就找管理员拿一把钥匙。**

### 🔑 `row_factory = sqlite3.Row` 有什么用？

**★ 比喻：仓库出库单的两种格式。**

```python
# ❌ 不设 row_factory（元组格式）——像这样给你东西:
#    "第0号物品、第1号物品、第2号物品"
#    你得自己记住"第1号是名字"
row = conn.execute('SELECT username, role FROM users').fetchone()
print(row[0])      # 'admin'   ← 我记得0是用户名吗？
print(row[1])      # 'admin'   ← 1是啥来着？

# ✅ 设了 row_factory（字典格式）——像这样:
#    "这是 username 物品、这是 role 物品"
#    名字直接标好了，不用记顺序
print(row['username'])   # 'admin'  ← 一目了然
print(row['role'])       # 'admin'
```

**★ 为什么要写成函数，不每次直接 connect？**
```
比喻：你不会每次要查仓库都自己跑去配一把新钥匙
     而是"找管理员拿钥匙"这一个固定流程

好处:
  ① 统一路径（搬家了只改一处）
  ② 统一格式（每次都带标签，不会忘）
  ③ 将来加安全措施（比如双人验证），只改这个函数
```

## 第 4 段：路由 —— "谁来了，谁负责接待"

### 4.1 装饰器是什么

```python
@app.route('/login', methods=['GET', 'POST'])
def login():
    ...
```

**★★★ 比喻：在门口挂一块牌子。**

```
┌─────────────────────────────────────┐
│  🪧 /login 这个窗口                   │
│  负责人：login 函数                   │
│  接受的业务：GET（询问）、POST（提交）  │
└─────────────────────────────────────┘

顾客走到 /login 这个窗口
   → 餐厅查牌子
   → 找到 login 这个负责人
   → 让他处理
   → 他端出来的东西就是给顾客的
```

**★ `methods=['GET', 'POST']` 是什么意思？**

**★ 比喻：窗口营业范围。**
```
不写 methods      → 只接待"询问"（GET）
写了 ['GET','POST'] → "询问"和"提交"都接待

★ 为什么登录要允许提交（POST）？
   询问（GET）  → "给我看看登录表格"
   提交（POST） → "我把填好的表格给你"
```

### 4.2 区分 GET 和 POST

```python
if request.method == 'POST':
    # 顾客提交了表格
else:
    # 顾客只是来看看
```

**★ 比喻：同一个窗口，两种业务。**
```
顾客空手来   → "给你一张空白表格"（GET 分支）
顾客交表格   → "我核对一下"（POST 分支）
```

### 4.3 取值

```python
username = request.form.get('username', '').strip()
password = request.form.get('password', '')
```

**★ 比喻：从顾客交的表格里，找对应的栏目。**

| 写法 | 比喻 | 结果 |
|---|---|---|
| `request.form['username']` | 表格里没这栏 → 你直接【摔桌子】 | ❌ 500 错误 |
| `request.form.get('username')` | 表格里没这栏 → 你【沉默】 | 返回 `None` |
| `request.form.get('username', '')` | 表格里没这栏 → 你写【空白】 | 返回 `''` |
| `...+ .strip()` | 顺便【擦掉多余的空格】 | ★ 最稳妥 |

**★ 为什么 `.strip()` 很重要？**

```
比喻：顾客写着" admin "（名字前后各有一个空格）
     你拿着" admin "去仓库查 → 查不到，因为仓库里存的是"admin"
     → 顾客会一脸懵："我明明没打错啊！"

.strip() 就是把名字两边的空格擦掉
```

### 4.4 ★★★ 数据库查询 —— SQL 注入的关键

```python
# ✅ 正确写法（参数化查询）
row = conn.execute(
    'SELECT * FROM users WHERE username = ? AND password = ?',
    (username, password)
).fetchone()
```

**★★★★ 这里用一个"点菜"的比喻来解释。**

#### ❌ 危险写法（字符串拼接）

```python
sql = f"SELECT * FROM users WHERE username = '{username}' AND password = '{password}'"
```

**★ 比喻：你给后厨写一张纸条，把顾客说的话【直接抄进去】。**

```
正常情况:
  顾客说"红烧肉"
  你写的纸条: 做一份【红烧肉】
  后厨: 好的，做红烧肉 ✅

恶意情况（SQL 注入）:
  顾客说: "随便，或者什么菜都行"
  你写的纸条: 做一份【随便，或者什么菜都行】
  后厨看了半天，理解成: "做随便什么菜或者什么都行"
  → 后厨真的随便做了一份给你 ✅（攻击成功）
```

**★ 再看真实的攻击：**
```
顾客在"用户名"栏填: admin' OR '1'='1
顾客在"密码"栏填: 随便

你抄进去的纸条变成:
   SELECT * FROM users
   WHERE username = 'admin' OR '1'='1' AND password = '随便'
                            ↑
                  这个条件【永远成立】！

后厨的理解: "用户名是 admin，或者 1 等于 1，这两个条件满足一个就行"
→ 1=1 永远成立 → 直接放行 → 不需要密码就登录了！
```

#### ✅ 安全写法（参数化查询）

```python
conn.execute(
    'SELECT * FROM users WHERE username = ? AND password = ?',
    (username, password)
)
```

**★★★ 比喻：不再抄纸条，改成【填表格】。**

```
餐厅准备了一张【印好的固定表格】:

  ┌──────────────────────────────────────────────┐
  │  客户姓名: [________]                         │  ← 只能填字，不能改格式
  │  密码:     [________]                         │
  │  查询条件: 姓名 = 上面那个 AND 密码 = 上面那个   │
  └──────────────────────────────────────────────┘

★ 顾客说的任何内容，只会被【填进空格里】
★ 就算他填 "admin' OR '1'='1"
  → 后厨只会理解成: "有个人名字叫 admin' OR '1'='1"
  → 查不到这个人 → 拒绝 ✅
★ 因为表格的【结构】是你提前定好的，顾客改不了
```

**★ 一句话记住：**
```
★ 字符串拼接 = 让顾客【口述菜名】，你可以乱理解
★ 参数化查询 = 给顾客【固定表格】，他只能填字
```

### 4.5 会话（session）—— "存包牌"

```python
if row:
    session['username'] = row['username']
    session['role'] = row['role']
    return redirect(url_for('welcome'))
```

**★★★★★ 这是最需要比喻的地方。**

#### 🎫 什么是 session？

**★ 比喻：超市的【存包牌】。**

```
问题: HTTP 协议是"金鱼记忆"——每次请求都是全新的
     你刚登录完，下次访问它就不认识你了

解决: 服务器给你一个【存包牌】

流程:
   ① 你登录成功
   ② 服务器把「用户名=admin, 角色=管理员」写进 session
   ③ 服务器把这个 session 盖个【防伪章】，变成一个字符串
   ④ 把这个字符串作为 Cookie 发给你的浏览器
   ⑤ 以后你每次来，浏览器自动带上这张牌
   ⑥ 服务器验章 → 认出你 → "哦，是管理员，请进"
```

**★★ session 存在哪？**
```
★ 存包牌上的【内容】存在【服务器】那边
★ 你手里的 Cookie 只是一个【签名过的凭证】
★ 所以叫"服务端会话"

对比（重要）:
   session  → 牌子的内容在服务器，你手里只有凭证
   cookie   → 内容就直接写在你手里的小票上
```

**★★★ 为什么说 Flask 的 session 是"签名"不是"加密"？**

**★ 比喻：信封上的【火漆印】。**

```
签名（Flask 默认）:
   → 内容【没封起来】，你撕开能看到里面写的字
   → 但火漆印是真的，你改了内容火漆就废了
   → 好处: 防篡改
   → 坏处: 内容能看（所以别放密码！）

加密（需要额外库）:
   → 内容也封起来了，你撕开也看不懂
```

**★ 你可以在 DevTools 里验证：**
```
F12 → Application → Cookies → session
复制那个值 → 用 Base64 解码 → 能看到 {"role":"admin","username":"admin"}
→ 这就是"签名不加密"的证据
```

### 4.6 错误提示的设计 —— "别告诉骗子太多"

```python
else:
    error = '用户名或密码错误'
```

**★★★ 比喻：小偷试钥匙，你别告诉他"这把锁根本不存在"。**

```
❌ 不好的提示:
   "用户 admin 不存在"  → 小偷知道: admin 不存在，换个名字试
   "密码错误"           → 小偷知道: admin 存在！可以针对性爆破密码

✅ 好的做法（代码里用的）:
   统一说"用户名或密码错误"
   → 小偷无法判断到底是哪种情况
   → 增加了攻击成本
```

**★ 这在安全领域叫"防用户枚举"。**

### 4.7 权限检查 —— "门口保安"

```python
@app.route('/welcome')
def welcome():
    if 'username' not in session:
        return redirect(url_for('login'))
    ...
```

**★★★ 比喻：贵宾区门口的保安查存包牌。**

```
★ 没有这段代码 = 贵宾区没人看门
   → 任何人直接走进去都能看（未授权访问漏洞）

★ 有这段代码 = 保安查牌
   → 没牌 → 请你回登录页
   → 有牌 → 请进
```

**★★★★ 这里有个极重要的概念：前端隐藏 ≠ 后端保护**

```html
<!-- welcome.html 里 -->
{% if role == 'admin' %}
<div>管理员面板</div>
{% endif %}
```

**★★★ 比喻：把金库门【刷成和墙一样的颜色】。**

```
★ 前端隐藏 = 把门刷成墙
   → 普通人看不见 → 但门还在那
   → 攻击者直接请求 /admin 接口 → 就进去了

★★ 正确做法 = 门口有真保安（后端检查）
   → 每个敏感接口都要检查 session['role']
   → 不能只靠前端"看不见"
```

**★ 铁律：**
```
凡是想"隐藏"的东西，都要在后端再检查一遍
前端的任何限制都只是【用户体验优化】，不是【安全措施】
```

# 四、HTML 模板讲解（菜谱模具）

## 🍰 什么是"模板"？

**★ 比喻：月饼模具。**

```
★ 你有一个【月饼模具】（login.html）
★ 每次做出来的月饼形状一样，但【馅可以不同】
★ 馅 = 后端传进来的变量

代码里:
   render_template('login.html', error='用户名或密码错误')
                                  ↑ 这个就是馅

   模板里写 {{ error }} 的位置
   → 会被替换成"用户名或密码错误"
```

## 4.1 Jinja2 三种语法

```html
双花括号 + 变量      → 输出变量的值（自动 HTML 转义，防 XSS）
百分号花括号 + 语句  → 逻辑控制（if / for / block）
井号花括号           → Jinja2 注释（内容不输出也不解析）
```

**★ 比喻：模具上的三种标记。**

```
双花括号   =  "这里留个洞，做的时候填馅"
百分号花括号 = "这是模具的开关（做/不做这一步）"
井号花括号  =  "这是模具上的笔记，做的时候不管它"
```

**★★★ 我踩的坑（重要！）：**

**★ 比喻：模具笔记写错了地方。**

```html
<!--
  这里如果写真的模板标签（百分号花括号那种）    ← ★★★ Jinja2 照样解析！
-->
```

**★ 为什么报错？**
```
比喻:
  HTML 注释（尖括号感叹号那种）是【给老鼠看的】（浏览器不显示）
  但 Jinja2 是【色盲】—— 它看不见 HTML 注释的标记
  → 它以为那是真的开关
  → 结果模具上多了一个未闭合的开关
  → 做月饼时机器傻了: "这个开关关在哪？"

报错: TemplateSyntaxError: Unexpected end of template
```

**★★ 正确做法：**
```
要写笔记，用井号花括号（这是 Jinja2 认的注释）
或者用文字描述，别写真的模板标签
```

## 4.2 `name` 属性 —— 表单的命脉

```html
<input type="text" name="username" id="username">
                   ↑              ↑
              后端靠这个取值    前端标签靠这个关联
```

**★★★ 比喻：快递单上的【收件人姓名栏】。**

```
★ input 标签 = 快递单上的一个空格
★ name 属性  = 这个空格旁边印的栏目名

<input name="username">  → 单子上印着"用户名: ______"
                            后端收到就能对上号

<input> 没写 name        → 单子上是个【没有标题的空格】
                            后端收到一头雾水: "这填的是啥？"
                            → 直接丢弃
```

**★ 最常见的错误：忘了写 `name`**
```html
<input type="text" id="username">        ← ❌ 后端收不到
<input type="text" name="username">      ← ✅ 正确
```

**★ 怎么验证？**
```
① 填完表单点提交
② F12 → Network → 找到 POST 请求
③ 看 Payload 里有没有 username
④ 没有 → name 写错了或没写
```

## 4.3 表单的 method 和 action

**★★★ `method` 的比喻：明信片 vs 信封。**

| 方式 | 比喻 | 安全性 |
|---|---|---|
| **GET** | 明信片 —— 内容写在【外面】，路上谁都能看 | ❌ |
| **POST** | 信封 —— 内容装在【里面】 | ✅ |

**★ 具体差别：**
```
GET  → 参数拼在 URL 上:
        /login?username=admin&password=123
        ★ 密码会出现在: 浏览器历史、服务器日志、代理日志
        ★ 就像把密码写在明信片上寄出去

POST → 参数在请求体里:
        /login
        Body: username=admin&password=123
        ★ 就像装在信封里
        ★ 注意: 仍然是明文！必须靠 HTTPS 才能真正保护
```

**★ `action` 的比喻：信封上写【寄到哪里】。**

**★ 为什么用 `url_for('login')` 而不是直接写 `'/login'`？**

**★ 比喻：用【通讯录】而不是【背电话号码】。**
```
写死 '/login':
   → 将来窗口改名成 '/signin'
   → 所有写死的地方都要手动改 → 容易漏

用 url_for('login'):
   → 通讯录自动查到新地址
   → 改一处，全站生效 ✅
```

# 六、常见错误排查表

**★ 排错心法：Flask 的报错堆栈会直接打印在终端里，最后一行通常就是根本原因。**

| 报错 | 比喻（病症） | 病因 | 药方 |
|---|---|---|---|
| `Unexpected end of template` | 模具上有个开关没关 | `if` 没配对，或注释里有模板标签 | 数 if / endif；检查注释 |
| `Encountered unknown tag` | 模具上写了个不认识的开关 | HTML 注释里写了模板标签 | 改用井号花括号注释 |
| `TemplateNotFound` | 找不到模具 | 文件不在 `templates\` 里，或名字拼错 | 检查目录和文件名 |
| `NameError` | 用了一个没准备的工具 | 变量没定义或忘了 import | 看报错行号 |
| `no such table: users` | 仓库里没有这个货架 | 没跑 `init_db.py` | 跑 `init_db.py` |
| `no secret key was set` | 没有防伪印章 | 没设 `app.secret_key` | 加上密钥 |
| `Address already in use` | 窗口已经有人占了 | 5000 端口被占用 | 换端口，或杀掉旧进程 |
| `request.form.get()` 返回 `None` | 快递单上没这个栏目 | input 少了 `name` 属性 | 加上 `name` |
| 登录成功但跳不回去 | 存包牌被前台拒收 | 浏览器禁用了 Cookie | 检查浏览器设置 |
| 500 但看不到原因 | 出事了但看不到现场 | `debug=False` | 暂时改成 `True` |

# 七、用 DevTools 观察登录过程（"装监控"）

**★ 比喻：在餐厅装监控，看顾客和厨房到底交流了什么。**

## 7.1 那两个勾选框的比喻

```
Preserve log（保留日志）
   → 不勾: 页面一跳转，监控录像就自动删了
   → 勾上: 跳转也不删（★ 必须，否则登录请求看不到）

Disable cache（禁用缓存）
   → 不勾: 浏览器可能直接读本地缓存，根本没发请求
   → 勾上: 每次都真的发（★ 必须）
```

## 7.2 看请求详情

| 标签 | 比喻 | 你能看到 |
|---|---|---|
| **Headers** | 信封的正面 | `Content-Type`、状态码 302 |
| **Payload** | 信封里的内容 | ★ `username=admin&password=admin123`（明文！） |
| **Response Headers** | 回信的正面 | ★ `Set-Cookie: session=eyJ...` |

**★★ 三个重要观察：**
```
① 密码在 Payload 里是【明文】
   → 比喻: 信封虽然是封着的，但用光照一下能看到里面
   → 所以真实网站必须用 HTTPS（相当于装甲车运送）

② 登录成功返回 302 而不是 200
   → 比喻: 前台说"请去3号窗口"，而不是直接把东西给你
   → 因为代码里是 return redirect(...)

③ Set-Cookie 里就是存包牌
   → 复制出来 Base64 解码，能看到里面的内容
```

# 十、一句话总结（全用比喻）

```
【整个 Web 开发】
   Flask = 餐厅
   路由 = 窗口
   模板 = 月饼模具
   数据库 = 仓库
   请求/响应 = 点菜单/端上来的菜

【三个最重要的知识点】

① 参数化查询（防 SQL 注入）
   ❌ 拼接   = 让顾客口述菜名，你可以乱理解
   ✅ 参数化 = 给顾客固定表格，他只能填字

② session（记住登录状态）
   = 超市存包牌
   内容在服务器（存包处），你手里只有凭证（牌子）
   改牌子上的字 → 火漆印对不上 → 被识破

③ 前端隐藏 ≠ 后端保护
   前端隐藏 = 把金库门刷成墙（门还在那）
   后端检查 = 门口有真保安
   ★ 凡是想藏的，后端都要再查一次

【排错】
   看终端里的报错堆栈，最后一行就是病因
```
